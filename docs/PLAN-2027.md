#### Engine as built (PR B)

Decisions made while building, on 2026-11-23, recorded for the owner. Item 4's message was reworded in PR C.

1. Left-out reasons are five: `unverified` and `no-spotify` (above), `no-tracks` (looked up, no own track found), `quota` (the newest-releases route stopped, on a quota answer or on a 429 that survived its retries, before the artist's lookup was complete, and no track of the artist's reached the playlist) and `lookup-failed` (a search or releases request for that artist failed and no track of the artist's reached the playlist). An artist with a track in the playlist is never left out.
2. Writes are never repeated on doubt. A POST is retried only on a 429 (Spotify answered and did nothing). A 5xx or no answer is not retried, because the request may have been carried out and a repeat could make a second playlist or add tracks twice. A create request that gets no answer, a 5xx, or a 2xx whose body is empty, not JSON or has no valid id resolves with `status: 'unconfirmed'`: no url, no id, no tracks added, exactly one create request. A playlist may exist, so the message names it and tells the visitor to look in Spotify before making another; it does not say to try again. `error.kind` is `'unconfirmed'` (never a rejection's kind such as `network`); the underlying cause (`network`, `http`, `response`) is in `error.cause`. A 401, 403, 429 or other 4xx on the create request rejects (nothing was created).
3. Search stops for everyone left (`searchStopReason`, the first reason seen, so it can depend on timing) for one of four reasons: `quota` (a 429 with `reason: "QUOTA_EXCEEDED"`), `rate` (any 429 that survived its 5 attempts), `errors` (3 searches in a row failed with a 5xx that survived its retries or a 200 whose body is not JSON; the constant is `SEARCH_ERROR_LIMIT`, like the lineup pipeline's "3 consecutive failures"; "in a row" is counted in the order searches finish, a search that works resets the count, so with 4 in flight it can depend on timing, and with 1 in flight it is exact) or `network` (a search whose fetch was rejected after 5 attempts, while Spotify is answering). Search is not retried; the remaining artists use the newest-releases route. For `network` the engine keeps run-wide evidence: every HTTP answer to any lookup request in the run, of any status, is counted. If the count rose while the failing search was running, the connection works and search stops at once. Otherwise that artist's newest-releases route is the probe: any answer proves the connection and stops search. If no probe request can be made (the route is used up, or the artist has no valid id) or it gets no answer, and the count did not rise, the lookup fails as offline: it rejects and nothing is created. Answers that arrived before the failing search began do not count (the connection may have dropped since). The result carries `searchStopReason` (`'quota'`, `'rate'`, `'errors'`, `'network'` or `null`) beside `searchExhausted`, which is true exactly when it is not null. The rule does not depend on reading `reason` in the browser: on 2026-11-23 the browser showed status 429 and the message "Too many requests"; reading `reason` there was not observed directly (the value was captured by a script outside the browser). A `rate` stop covers that case. Cost before the switch: `rate` is 5 requests and 4 waits of 1 to 30 s each (worst case 120 s, typically about 4 s); `network` is 5 requests and 4 waits totalling 7.5 s, and up to 4 artists pay it at once; `errors` is 3 failed searches of 5 requests each (15 in all at 1 in flight, up to 20 at 4). The newest-releases route stops for everyone (`releasesExhausted`, with `releasesStopReason` `'quota'` or `'rate'`, the first seen) on a `quota` answer or on a 429 that survived its retries, on any albums or tracks request; the artists not yet served are left out as `quota`. A 5xx or a 404 there fails one request for one artist only. An expired login (401), a refusal (403) or no connection stops everything before anything is created.
4. Quota detection applies to every request through `createApi`, so the library import now fails at once on a 429 that carries the quota reason instead of after about five waits. The message was reworded in PR C (see "Interface as built (PR C)", item 8).
5. When no track is found at all, nothing is created (`status: 'empty'`).
6. A failure while adding tracks resolves with `status: 'incomplete'`, the link and the counts of what was added. The four statuses are `created`, `incomplete`, `empty` and `unconfirmed`. For `incomplete`, `error.kind` is `'incomplete'` and the engine writes its own message (the playlist was made, not every track was added, open it in Spotify); it does not use the wrapper's text, which says to try again. The failure's kind (`auth`, `forbidden`, `rate`, `quota`, `http`, `network`) is in `error.cause`. PR C reads `status` first: only `incomplete` and `unconfirmed` carry an `error`, and its `kind` is never one a rejection has, so the two cannot be taken for a rejection.
7. The date in the playlist name is the visitor's local date written like "Nov 23, 2026": "Spotifort: Treefort 2027 · Nov 23, 2026".
8. Known limit: the releases request returns albums before singles, 10 in all, so for an artist with 10 or more albums a newer single is not seen. Asking for albums and singles separately would fix it; not done because that form has not been live-tested.
9. `newestReleases` lists only artists with a newest-releases track actually in the playlist: a track dropped as a duplicate of an earlier artist's, or in a batch that was not added, does not count.
10. After a failure while adding, `trackCount` is a lower bound: the failed batch is not retried and may have been applied.
11. Request volume: one search per artist (4 artists in flight); the newest-releases route costs up to 4 more requests per Spotify id (1 for the releases, up to 3 for their tracks).
12. Shared tracks. When two lineup artists share a track, the artist earlier in page order keeps it. Lookup runs in steps: search for everyone; allocate in page order; top up artists still short from their remaining search results and then from newest releases (skipping tracks already taken); allocate again in page order. The result does not depend on the order in which answers arrive. An artist whose only own tracks are held by an earlier artist is not left out: it is padded with the shared track, which appears once in the playlist. Padding uses only tracks claimed by an earlier artist in page order, so a track a later artist holds is never placed under an earlier one (that could split the later artist's block). Known limit: two artists that both went straight to newest releases (search failed or stopped) and share a release track can end one track short.
13. A progress callback that throws is caught and ignored, in the lookup, the create step and the add step: a display error cannot reject the lookup, leave other workers running or stop the adding of tracks.
14. Versions of one song across two artists: when a track an artist shares with an earlier artist is given to that earlier artist, every other version of the same song (same song key) in this artist's own candidates is skipped too, so "Duet" and "Duet - Live" do not both reach the playlist. Song keys are never compared between artists: two artists may each have a song called "Home".

Notes for PR C (all taken up; see "Interface as built (PR C)"): keep one creation in flight (disable the button; a double click must not make two playlists: two `createPlaylist` calls at once make two playlists); render track and artist names from Spotify with `textContent`; reword the quota message; read `status` before `error`, and word the `unconfirmed` and `incomplete` outcomes for the visitor (neither may say to try again); word the four `searchStopReason` values (`quota`, `rate`, `errors`, `network`) and the two `releasesStopReason` values (`quota`, `rate`) for the visitor; the engine takes the year and the date from the caller. Also tracked: no `market` is sent and `is_playable` is not checked, so a track unavailable in the visitor's country could be picked; version collapsing has edge cases ("Home" and "Home - With Friends" are merged; "Song (Piano)", "Song - Spotify Singles", "Song feat. Bob" and "Song -Live" are not collapsed). Known behaviours, not fixed: in-flight retries inside `createApi` cannot be cancelled, so after a fatal error up to 3 other in-flight requests finish their retries (no new artist starts and no progress is emitted); `searchStopReason` keeps the first reason seen, so it can depend on timing; one artist's failed search (after 5 tries) moves every remaining artist from 1 request to up to 4. The offline limit of the search probe: if a search gets no answer and no other request was answered while it was failing, and the newest-releases route cannot be tried for that artist (it has stopped, or the artist has no usable Spotify id), the lookup ends as offline even though Spotify answered earlier in the run. The engine cannot tell this from a dropped connection.

#### Interface as built (PR C)

Decisions made while building, on 2026-11-23. The owner has not decided them; they are what the preview shows and are open to change.

1. Where the purpose of a login is kept. A login is for the library or for a playlist, and each asks only for its own scopes. The purpose rides in the OAuth `state` value (`<random>.<purpose>`), which was already kept in `sessionStorage` for the redirect, so no new key is stored. The page acts on it only after the returned `state` matched the stored one. A state with no known purpose is a library login.
2. Once, not twice. After the login the playlist is created straight away. Finishing the login removes the state and the verifier and replaces the callback URL with `/`, so a reload, or going back, has nothing to act on. No flag is stored.
3. One login, one set of permissions. A playlist login cannot refresh the library and a library login cannot make a playlist; the other action logs in again (Spotify skips its consent screen for permissions already approved). A token with the playlist permission that is still in memory is reused: the button then reads "Make the playlist" and there is no redirect.
4. The Client ID in the panel. A saved Client ID is used as it is, with "Use a different one" to change it. Without one, the panel shows the field, the "Remember my Client ID" checkbox and the links to `/setup` and `/why`.
5. No cap on the size. The playlist covers every Treefort pick. After a full library import the picks can be most of the lineup: about 190 artists is about 570 tracks and about 190 searches, most of the one day's search count that was seen to exhaust the quota (about 300). From 100 artists up the panel says that the limit may be reached and what happens then. Whether to cap the playlist (for example the matches plus the strongest recommendations) is not decided; see "Open items for the owner".
6. Wording of outcomes. `created`: "Your playlist is ready", the counts, the name, "Open Spotify". `incomplete`: "Your playlist was made, but it is not complete", "at least N of M tracks", and that making a playlist again would create a second one. `empty`: "No playlist was made". `unconfirmed`: "We cannot tell whether your playlist was made", look in Spotify for the name before making another, and if it is there it is empty. Neither `incomplete` nor `unconfirmed` says to try again. Every rejection says that nothing was created. A `rate` stop is worded as possibly a daily limit, because the browser may not be able to tell the two apart.
7. Left-out picks are grouped by reason (`unverified`, `no-spotify`, `no-tracks`, `quota`, `lookup-failed`), each artist with its usual listen or search link for the chosen service. Artists that got tracks from newest releases are named in one sentence.
8. The limit messages. A quota answer now reads "Spotify's daily limit for your Client ID has been reached. It can take up to a day to clear." A 429 that survived its retries reads "Spotify is refusing requests right now (too many requests). Wait a while before trying again; if it is a daily limit, it can take up to a day to clear." Both also show for the library import. "For your Client ID" is the visitor's word for it; the quota is counted per developer account.
9. If the similar-artist data cannot be loaded after the login, nothing is created (the recommendations would be missing) and the visitor is told so.
10. `market` and `is_playable` (tracked in PR B): not sent and not checked, decided without the owner because there is no safe way to do it yet. `GET /me` no longer returns `country`, `available_markets` is gone from responses, and `market=from_token` has not been live-tested: if Spotify refused it, every search would fail. The effect of leaving it out is that a track not playable in the visitor's country could be picked and would show greyed out. In development the lookup log lists the field names of the first search track, so the local test shows whether `is_playable` is there to use.
11. Version collapsing (tracked in PR B): "Song (Piano)", "Song - Spotify Singles", "Song - Recorded at ...", and a bare trailing "feat.", "ft." or "featuring" credit now collapse into "Song". Still known: "Home" and "Home - With Friends" are merged (a featured credit and a different song cannot be told apart), and "Song -Live" (no space after the dash) is not collapsed. The cost of either is one track that is a version of another, or one track fewer for an artist.
12. The words Spotify's consent screen uses ("Create, edit, and follow private playlists") are quoted in the panel and on `/setup` as Spotify's wording. Nothing Spotifort makes is called a private playlist.

## Working rules

- **Roles.** The main Claude session architects, orchestrates and manages the project. Coding is delegated to Opus/Sonnet agents (Sonnet for routine work, Opus for harder pieces). The main session reviews every diff before reporting work as done.
- **Updated and secure.** Every phase includes a dependency check (`npm audit`, `npm outdated`) and a security review of the changes before merge. Findings are fixed in that phase or recorded here with a reason.
- **Branches and pull requests.** `main` auto-deploys to spotifort.com and is protected: no direct pushes, no force pushes, no deletion, for admins too. All work, including docs, lands through a pull request from a branch, and merges only after the Cloudflare preview deployment for that PR has been checked.
- **Merging.** Agreed 2026-11-13: Claude merges a pull request once automated checks pass, the diff is reviewed, and the Cloudflare preview is checked, and reports each merge. A change that substantially alters what visitors see (PR 2.6, and the playlist interface PR C) waits for the owner to look at the preview first.
- **Secrets.** Never committed. Local secrets go in `.env.local` (gitignored); CI secrets go in GitHub Actions secrets.

**Small things noticed, not done**

- Owner report, 2026-11-23: typing "Green Day" offers nothing in the search box and ends at the no-data message. Cause: the similarity index holds only artists that appear in some lineup artist's Last.fm similar list at a match of 0.1 or more, and Green Day is in none of the stored lists at any score. The same is true of The Beatles, Taylor Swift, My Chemical Romance and The Offspring; Radiohead appears once at 0.07, under the cutoff. Of ten very well-known names checked, five are missing. This is the index working as designed (see `docs/ARCHITECTURE.md` on artists with no hits), but to a visitor a famous name with no result reads as broken. Not decided. Options to weigh: wording for the no-data message that explains it and offers that artist's genres; PR 2.7 (live Last.fm tags for a typed name, feeding the genre fallback), which this is a reason to reconsider; a one-off live check of Green Day's own Last.fm similar list for lineup artists.
- The playlist engine's releases request returns albums before singles, so a newer single of an artist with 10 or more albums is not seen (decision 8 under "Engine as built (PR B)"). Asking for albums and singles separately would fix it; not live-tested.
