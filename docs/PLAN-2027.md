### Playlist creation (decided 2026-11-23; engine built, interface not yet)

The owner decided the following on 2026-11-23 after live tests (`docs/research/spotify-playlist-live-tests-2026-11.md`). Terms are defined in `CONTEXT.md`.

| Area | Decision |
|---|---|
| Priority | Playlist creation is the next feature, ahead of the Tidal proof-of-concept. The Tidal item stays, after it. |
| Content | The Treefort picks: Playing Treefort, then Recommended for you strongest first, in page order, each artist's tracks together. |
| Tracks per artist | 3 |
| Left out | Unverified lineup artists and artists with no Spotify page get no tracks. They are named to the visitor afterwards with their usual listen or search links. |
| Where tracks come from | Looked up in the browser when the visitor asks, with the visitor's own token. Nothing about tracks is precomputed, shipped or stored. Reasons: Spotify's terms on storing content, and the pipeline's own search quota. |
| Track choice | Search by artist name. Keep only tracks that carry the lineup artist's Spotify id. Prefer tracks where that artist is listed first. Treat versions of one song as one. Take 3. If fewer than 3, fill from the artist's newest releases (sorted by release date by the app, since the API groups by type). |
| Quota running out | If the visitor's search quota runs out mid-lookup, continue with newest releases for the remaining artists, create the playlist and say which artists got newest songs. If that also runs out, create it with what was found and name the rest. |
| Failure | All lookups finish before the playlist is created, so a failure leaves nothing in the visitor's account. |
| Control | A button "Make a Spotify playlist" beside "Share my picks", shown to every visitor with results. A visitor without a Client ID is led through the existing setup. Not on the Shared picks view in the first version. |
| Permission | Only `playlist-modify-private`, requested on click (already this plan's rule). A visitor who only typed artists never grants library access. |
| Before login | A short panel says what will happen (one playlist, about N tracks from M artists, nothing else changed) and what Spotify's consent screen will say. Continue starts the login. |
| After login | The playlist is created straight away, once, with a progress line. A reload does not create a second one. |
| Visibility | Created off the visitor's profile (`public:false`). The API cannot make it private, so the page says plainly that Spotify labels it public, that anyone with the link can open it, and how to choose "Make private" in Spotify, with a link to the playlist. The words "private playlist" are not used for what Spotifort creates. |
| Name and storage | Name "Spotifort: Treefort <year> · <date>" (year from the festival config). Description "Made with spotifort.com. Not affiliated with Treefort Music Fest or Spotify." A new playlist every time. Nothing about playlists is stored. |
| After creating | An "Open Spotify" link (Spotify's permitted wording), counts of tracks and artists, and the left-out list. |

#### Engine as built (PR B)

Decisions made while building, on 2026-11-23. The owner has not seen them; open to change in PR C.

1. Left-out reasons are five: `unverified` and `no-spotify` (above), `no-tracks` (looked up, no own track found), `quota` (Spotify's limit ran out before the artist could be looked up) and `lookup-failed` (a request for that artist failed).
2. Writes are never repeated on doubt. A POST is retried only on a 429 (Spotify answered and did nothing). A 5xx or no answer is not retried, because the request may have been carried out and a repeat could make a second playlist or add tracks twice. So a create request that fails this way is reported as a failure although, rarely, an empty playlist may exist.
3. Only a 429 with `reason: "QUOTA_EXCEEDED"` switches the remaining artists to the newest-releases route (search) or stops that route (albums). It is never retried. Any other failed request (plain 429 after the usual retries, 4xx, 5xx, unreadable body) affects one artist only. An expired login (401), a refusal (403) or no connection stops everything before anything is created.
4. Quota detection applies to every request through `createApi`, so the library import now fails at once on a quota 429 instead of after about five waits. The message ("Spotify is busy right now. Please try again in a minute.") is unchanged and is wrong for a limit that lasts about a day; rewording it belongs to PR C.
5. When no track is found at all, nothing is created (`status: 'empty'`).
6. A failure while adding tracks resolves with `status: 'incomplete'`, the link and the counts of what was added.
7. The date in the playlist name is the visitor's local date written like "Nov 23, 2026": "Spotifort: Treefort 2027 · Nov 23, 2026".
8. Known limit: the releases request returns albums before singles, 10 in all, so for an artist with 10 or more albums a newer single is not seen. Asking for albums and singles separately would fix it; not done because that form has not been live-tested.
9. `newestReleases` lists only artists with a newest-releases track actually in the playlist: a track dropped as a duplicate of an earlier artist's, or in a batch that was not added, does not count.
10. After a failure while adding, `trackCount` is a lower bound: the failed batch is not retried and may have been applied.
11. Request volume: one search per artist; the newest-releases route costs up to 4 more requests per Spotify id (1 for the releases, up to 3 for their tracks).

Notes for PR C: keep one creation in flight (disable the button; a double click must not make two playlists); render track and artist names from Spotify with `textContent`; reword the quota message; the engine takes the year and the date from the caller.

## Working rules

- **Roles.** The main Claude session architects, orchestrates and manages the project. Coding is delegated to Opus/Sonnet agents (Sonnet for routine work, Opus for harder pieces). The main session reviews every diff before reporting work as done.
- **Updated and secure.** Every phase includes a dependency check (`npm audit`, `npm outdated`) and a security review of the changes before merge. Findings are fixed in that phase or recorded here with a reason.
- **Branches and pull requests.** `main` auto-deploys to spotifort.com and is protected: no direct pushes, no force pushes, no deletion, for admins too. All work, including docs, lands through a pull request from a branch, and merges only after the Cloudflare preview deployment for that PR has been checked.
- **Merging.** Agreed 2026-11-13: Claude merges a pull request once automated checks pass, the diff is reviewed, and the Cloudflare preview is checked, and reports each merge. A change that substantially alters what visitors see (PR 2.6, and the playlist interface PR C) waits for the owner to look at the preview first.
- **Secrets.** Never committed. Local secrets go in `.env.local` (gitignored); CI secrets go in GitHub Actions secrets.

**Small things noticed, not done**
- Autocomplete ranks outside artists by how many lineup artists they link to, so a lesser-known name can lead a famous one ("black" lists Black Ends above Black Pumas). There is no popularity figure for outside artists.
- Owner report, 2026-11-23: typing "Green Day" offers nothing in the search box and ends at the no-data message. Cause: the similarity index holds only artists that appear in some lineup artist's Last.fm similar list at a match of 0.1 or more, and Green Day is in none of the stored lists at any score. The same is true of The Beatles, Taylor Swift, My Chemical Romance and The Offspring; Radiohead appears once at 0.07, under the cutoff. Of ten very well-known names checked, five are missing. This is the index working as designed (see `docs/ARCHITECTURE.md` on artists with no hits), but to a visitor a famous name with no result reads as broken. Not decided. Options to weigh: wording for the no-data message that explains it and offers that artist's genres; PR 2.7 (live Last.fm tags for a typed name, feeding the genre fallback), which this is a reason to reconsider; a one-off live check of Green Day's own Last.fm similar list for lineup artists.
- The playlist engine's releases request returns albums before singles, so a newer single of an artist with 10 or more albums is not seen (decision 8 under "Engine as built (PR B)"). Asking for albums and singles separately would fix it; not live-tested.
- The quota message ("Spotify is busy right now. Please try again in a minute.") is wrong for a daily quota and now also shows for the library import; reword it in PR C.
- The footer still shows a "Powered by Spotify Web API" badge although Spotify is now optional.
- `/favicon.ico` returns 404 (pages use the PNG logo).
- The event shape for the schedule follows the vendor's documented schema but has never been tested on real events.
- `scripts/lineup-lastfm.js` has a stale header comment mentioning `.cache/lastfm`.
- The name "Spotifort" is to be revisited after the festival. Spotify's Developer Policy says an app name "should not begin with 'Spot'"; how it applies is unknown (`docs/research/spotify-api-availability-2026-11.md`, section 6.1).
- The three unverified artists could be hand-checked in `overrides.json`; each one fixed is one fewer left out of a playlist.
- The lineup job's artist search shares Spotify's search quota (about 300 a day per developer account was enough to exhaust it). A manual job run or heavy testing on the same developer account on the same day can make the job's search fail with 429; the stages stop after three failures and retry next run.
