## Decisions

| Area | Decision |
|---|---|
| Audience | Public Treefort attendees |
| Backend rule | Stateless Cloudflare Pages Functions allowed. No user data stored or logged server-side. |
| Default experience | No login: type artists you like, get Treefort recommendations |
| Artist entry | Autocomplete from a shipped static index; live Last.fm search (via Pages Function) for names not in it |
| Similarity | Build-time Last.fm similar-artist lists and tags for every lineup artist, shipped as static JSON. Live Last.fm lookup for unknown artists. Tag overlap as last fallback. |
| Input model | One shared, editable "my artists" pool fed by every source |
| Results | Two ranked lists ("Playing Treefort", "Recommended for you") with "because you like X" reasons. The [+] expansion stays. |
| Spotify | Optional upgrade using the existing bring-your-own-Client-ID flow. Reads Liked Songs, top artists and followed artists. |
| Other platforms | Tidal first, starting with a proof-of-concept; dropped if it caps users. Apple Music decided after Tidal. No YouTube Music. No Last.fm-username login. |
| Matching | By platform ID. Name-only matches are shown and marked unconfirmed. |
| Lineup updates | Scheduled GitHub Action opens a PR with a report of low-confidence matches. Corrections live in an overrides file the pipeline always respects. |
| Outputs | Listen links per platform; share link (Treefort picks only, encoded in the URL); playlist creation (write permission requested only on click); schedule and venues |
| Persistence | Client ID and artist picks in `localStorage`. Access tokens never stored. |
| Stack | Vanilla JS + Vite, plus Vitest. One adapter module per platform, all returning the same shape. |
| Year handling | Per-year data file and a single festival config. Only the current year is shown. |
| Name | Spotifort stays for 2027; revisit after the festival |
| Money | Non-commercial, with a Last.fm credit |

### Assumptions (not separately confirmed)

- Each lineup artist gets a platform-neutral record: own ID, MusicBrainz ID, per-platform IDs. IDs are resolved through MusicBrainz URL relationships, with name search as fallback.
- The new pipeline does not depend on Spotify's deprecated `genres` field.
- The live-lookup Pages Function is rate-limited and caches artist lookups only.
- Site copy changes from "no backend" to "nothing stored", and states that typed artist names are sent to Last.fm.
- Schedule and venues are designed once Treefort publishes the schedule.

## Working rules

- **Roles.** The main Claude session architects, orchestrates and manages the project. Coding is delegated to Opus/Sonnet agents (Sonnet for routine work, Opus for harder pieces). The main session reviews every diff before reporting work as done.
- **Updated and secure.** Every phase includes a dependency check (`npm audit`, `npm outdated`) and a security review of the changes before merge. Findings are fixed in that phase or recorded here with a reason.
- **Branches and pull requests.** `main` auto-deploys to spotifort.com and is protected: no direct pushes, no force pushes, no deletion, for admins too. All work, including docs, lands through a pull request from a branch, and merges only after the Cloudflare preview deployment for that PR has been checked.
- **Merging.** Agreed 2026-11-13: Claude merges a pull request once automated checks pass, the diff is reviewed, and the Cloudflare preview is checked, and reports each merge. A change that substantially alters what visitors see (PR 2.6) waits for the owner to look at the preview first.
- **Secrets.** Never committed. Local secrets go in `.env.local` (gitignored); CI secrets go in GitHub Actions secrets.

**Change from the design interview (2026-11-13):** the interview chose "precomputed plus live" similarity. The data spike showed a live Last.fm lookup adds almost nothing over the static index (see `docs/ARCHITECTURE.md`), so the new experience ships fully static and the live function moves to the end as an optional extra.

How each piece works is specified in `docs/ARCHITECTURE.md`.

Carried in from Phase 1 and folded into the PRs above: parallel library fetch with progress (2.6), generated or removed landing preview (2.6), de-duplicated `callback.html` (2.6).

Apple Music decision, playlist creation, schedule and venues.

### Notes carried into Phase 2

- Fetching a large library is slow: 2,998 liked songs took 60 sequential requests. Add progress and consider parallel pages.
- The landing-page "what you'll see" preview is hardcoded HTML in `index.html` and `callback.html` and must be hand-updated each year; generate it from lineup data or drop it in the redesign.
- `callback.html` is a near-duplicate of `index.html`.
- Borderline non-genre tags ("female vocalists", "queer", "kids") were kept by the Phase 1 filter.
